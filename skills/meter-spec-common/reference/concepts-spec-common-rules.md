# 仕様書共通ルール
## 変更履歴情報の扱いルール
- 仕様書内に記載される変更履歴情報や変更履歴シートは、無効情報として扱うこと。
- 変更履歴情報は"変更履歴"、"変更概要"、"更新履歴"、"Revision history"等の名称でシート名や章節名になっている。

## 機能有無判定ルール
- メータ機能の有無を切り替えるための判定である。
- 機能有無判定は、機能有無判定用信号を機能有無判定時間内に2回連続受信で成立となる。
- 機能有無判定時間は、機能有無判定用信号の「通信周期(msec) × 2.1 (切上げし100msec単位としたもの)」で設定される。
- "通信周期"は、"送信周期"や"受信間隔"など同義語で記載されることもある。
- 機能有無判定の設定規則は以下の通り。
  - 「通信途絶判定後にセットする値が指定されており、かつその値が表示有り/吹鳴有りの実施条件になっている」を満たす場合、機能有無判定「あり/○」の設定必要。
  - ソフトSWの制御機能の場合、機能有無判定「あり/○」の設定必要。
  - 上記以外の場合、 機能有無判定の設定は不要。
- 機能有無判定は"機能有無判別"と記載されることもある。

## 通信途絶(判定)時間のルール
- 通信途絶(判定)時間は以下のどちらか大きい値で設定される。
  - 3600(msec)
  - 対象信号の「通信周期(msec) × 5 (切上げし100msec単位としたもの)」で設定される。

## 実施条件の記載ルール
- 実施条件はデータラベルとビットの組み合わせで記載する。
- 但し、データラベルとビットの組み合わせで記載できない場合に限り、他章節への参照を記載してもよい。
- 複数のビット定義がある場合は、ANDまたはORで記載を行う。
- 以下に記載形式の代表例を示す。
  - 完全一致型（例：信号名 = 00b）
  - ワイルドカード型（例：信号名 = *1b）
    実施条件定義不足の例：2bitの通信信号に対し実施条件に`*1b`, `1*b`と記載されている場合、`00b`のパターン定義が不足している
  - プレースホルダ型（例：信号名 = %1b）
    実施条件定義不足の例：2bitの通信信号に対し実施条件に`%1b`, `1%b`と記載されている場合、`00b`のパターン定義が不足している
  - エッジ型（ビット値が00から01変化時の例：信号名 = 00b → 01b、または　信号名 = 00b->01b）

## 【】で囲まれた文字列:
1. 【】で囲まれた文字列は定数名である可能性がある。ユーザープロンプトまたは調査の過程で【】で囲まれた文字列が出現した場合は、`skills/general-rule/SKILL.md` の「### 固有ラベル名の検索:」の処理を実施し、全ファイル横断の厳密収集と対象文書の深掘りを行う。
2. 定数は通信信号とは異なる。通信信号として定義がないことは問題にしないこと。

## 信号（データラベル, メッセージラベル）名、定数名、フレーム名・メッセージID、MCUIDが含まれる場合:
ユーザープロンプトまたは推論過程で、回答に関連しうる信号・定数・フレーム・メッセージ名/ID・MCUID等の識別子が出現した場合、@参照の有無や情報出所に依らず `skills/general-rule/SKILL.md` の「### 固有ラベル名の検索:」の処理を実施し、全ファイル横断の厳密収集と対象文書の深掘りを行う。
