# チェック項目No.
CHK-202

# チェック項目
参照先仕様書の記載が必要ないかを確認する。

# チェック判定仕様

本チェックは、参照先仕様書の記載漏れを、着眼点の異なる次の2つの観点で確認する。
両観点をそれぞれ実施し、いずれかの観点で「問題あり」もしくは「要確認」となった場合は全体を「問題あり」と判定する。
両観点で「問題なし」となった場合のみ全体を「問題なし」と判定する。

- 観点A：仕様変更点にフォーカスし、変更点のキーワードから関連仕様書を探して、参照先に記載されているかを確認する。
- 観点B：仕様変更点と関連する対象にフォーカスし、その対象を定義する仕様書を探して、参照先に記載されているかを確認する。

## 観点A：仕様変更点にフォーカスした関連仕様書の記載漏れ確認
（仕様変更点のキーワードから関連仕様書を探し、それらが参照先に記載されているかを確認する）

A-1. 仕様差分内容から、機能名やIDといったキーワードを抽出する。
     - キーワードは、before_markdown と after_markdown を対比し、実際に変化した箇所（追加・変更されたセル/トークン）のみから抽出する。
     - 同じ差分レコード（行・章節）内に含まれていても、before と after で一致する（＝未変更の）セル・記載からはキーワードを抽出しないこと。
     - 抽出対象は、**固有名詞的な機能名・ID・仕様書名（特定の対象を一意に指す語）**に限定する。「機能有無判定」「ステアリングSW押下制御」「表示」等の**汎用的な機能概念語（複数仕様書で一般的に用いられる一般概念語）は、それ単独ではキーワードとして抽出しない**（他仕様書との偶発的な一致＝偽陽性ヒットの原因となるため）。
A-2. 機能名やIDといったキーワードを使用し、全ての仕様書に対してハイブリッド検索(`graph_search_hybrid`)を実施する。そのキーワードで検索できた仕様書名を抽出する。
     - 抽出したキーワードは1語ずつ個別に検索する（複数語を1クエリにまとめない）。各回の検索でヒットした仕様書名を、重複を除いて1つのリストにまとめてA-3の対象とする。
     - ヒットのうち、**汎用概念語の一致による別文脈のヒット（偽陽性）は、関連仕様書として数えず A-3 の判定対象から除外する**。具体的には、ヒット箇所の本文が仕様変更点と異なる機能・文脈を扱っており、当該変更が実際に関連する対象を指していない場合は偽陽性とみなす（例：変更点「HUD有無判定」に対し、汎用語「機能有無判定」で偶発ヒットした「タコメーター機能有無判定」等）。偽陽性か否かはヒット箇所の本文を確認して判断し、除外した場合はその根拠を判定理由に明記する。
     - チェック対象仕様書自身の版違い（自己参照ヒット）も、参照先記載漏れの判定対象から除外する。
A-3. 検索できた仕様書名が、チェック対象仕様書内の該当キーワードが記載されている章節内と同じ章節内に記載があれば、「問題なし」と判断し、記載がなければ「問題あり」と判断する。
     - 「同一章節内に記載あり」と判断できるのは、**仕様書名そのもの**が当該章節内に記載されている場合に限る。
     - **"要求ID"欄／"要求ID(#文言No)"欄に現れる文言（およびその接頭辞）は、仕様書名の記載とは見なさない**。
A-4. 上記A-2で作成したリスト全件に対してA-3を実施し、全件「問題なし」であれば「問題なし」、1つでも「問題あり」があれば「問題あり」とする。

## 観点B：仕様変更点と関連する対象にフォーカスした仕様書の記載漏れ確認
（仕様変更点が扱う対象を定義する仕様書を探し、それが参照先に記載されているかを確認する）

B-1. 仕様変更箇所が参照先へ委ねている対象（機能・表示物・項目・定義等）を特定する。
     - 参照先仕様書が1つも記載されていない場合（空欄・「-」・TBD・未定等）は、委譲対象が無いものとして本観点は対象外とし、「問題なし」とする。
B-2. 記載された各参照先仕様書の本文を取得し、B-1の対象「そのもの」を定義する参照先があるかを確認する。
     - 当該対象を定義する仕様書を探索範囲内で特定して判定理由に明記する（探索範囲内に見つからない場合は断定せず「要確認」とする）。
     - 対象の一部の部品・付随条件のみを定義する参照先は該当としない。
     - 参照先名が記載されている事実のみで整合と判断せず、必ず本文で確認すること。
B-3. 対象そのものを定義する参照先仕様書名が、当該対象と同一章節内に記載されていない場合は「問題あり」、記載されている場合は「問題なし」とする。
