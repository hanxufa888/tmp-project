# チェック項目No. 
CHK-076

# チェック項目
今回の変更点に対し、同じ仕様書内の他の機能に変更が必要ないか確認したか？
(e.g. TT点灯と同時にブザーを吹鳴させる際に、TTの点灯条件のみを変更しブザー吹鳴条件の修正を忘れていないか)

# チェック判定仕様
## 変更種別による分岐（最初に判定する／必須）
本チェックの条件分岐は、**変更点（セル／項目）単位**で判定する。差分レコード（行）単位ではない。
- 対象差分に含まれる各変更点について、変更種別を個別に判定し、対応する条件を実施する。
  - 変更前に当該セル／項目の記載が存在し、その記載が変更または削除された変更点 → **`<記載変更・削除の場合>`** を実施する。
  - 変更前に当該セル／項目の記載が存在せず（空欄等）、新規に値が追加された変更点 → **`<記載追加の場合>`** を実施する。
- 排他は「1つの変更点」単位で成立する（1つの変更点は「変更・削除」か「追加」のいずれか一方）。一方、1つの差分レコード内に種別の異なる変更点が混在する場合（例：同一行内で、ある項目は値変更・別の項目は空欄→値の追加）は、**各変更点に対応する条件をそれぞれ実施する**（両条件が併用されうる）。
  - 例：表示種類「画像→－」「色 umber→red」（＝変更点：変更・削除）と、「他:特別条件 空欄→○（Detailed Spec2参照）」（＝変更点：追加）が同一行に併存する場合、前者群には `<記載変更・削除の場合>`、後者には `<記載追加の場合>` を適用する。
- 最終判定は、実施した全変更点・全条件の結果を統合して決定する（いずれかの変更点で問題ありがあれば「問題あり」、いずれかが確定不能なら「要確認」、全て問題なしなら「問題なし」）。ある変更点に適用されない条件を理由に「問題あり」/「要確認」としてはならない。

## 共通原則（網羅抽出の徹底）
- 「同一もしくは類似する記載」の抽出は、最初の一致や代表例で打ち切ってはならない。変更後仕様書（仕様書本体・添付資料）全体を走査し、同じセット記載構造（同一シート/章節フォーマット・同一項目(列)・同一要求IDパターンの行群など）に属する箇所を**全件**列挙すること。
- 列挙時は各箇所の所在（ファイル・シート・章節・要求ID/行）と現記載値を一覧化し、判定理由に**全件**を明記する。代表例のみの提示・一部省略・「他多数」等での集約を禁止する。
- 「同様の変更が必要か」の判定で参照元の条件（例：機能有無判定、電源状態、適用条件、要求廃止有無）を確認する必要がある場合は、当該参照元を参照する。参照元行が要求廃止（無効情報）の場合は有効な記載として扱わない。

## チェック対象外（他チェック項目との切り分け／重複防止）
以下の観点は本チェック(CHK-076)の対象外とし、検出・指摘しない。
- 変更点が Detailed Spec / Detailed Spec2 / Detailed Spec3 シートの「特別処理」の追加・変更・削除である場合に、当該特別処理に対応する参照元シート（TT/BZR/MID/Variable_MID/SW）の同一要求行（`meter-spec-common` の `guide-newformat-sheetsection.md` が定める 機能ブロック↔特別処理指示 の対応キー＝章節番号・No. で対応づく行）の項目「他:特別条件（Refer to Section*）」フラグ（〇/×）が、特別処理の有無と整合して更新されているか、という整合確認。
  - これは **CHK-026**の担当範囲であるため、CHK-076では判定しない。

## `<記載変更・削除の場合>`
1. 仕様変更個所の変更前の記載に対し、同一もしくは類似する記載を変更後仕様書内(仕様書本体、添付資料を含む)全体から**網羅的に**抽出する。
  - 抽出は上記「共通原則」に従い、同一セット記載構造の全箇所を列挙する（代表例で打ち切らない）。
  - 同一もしくは類似する記載がある場合は次の確認に進み、無い場合は「問題なし」と判断する。
2. 抽出した同一もしくは類似する記載の**各々**に対し、今回の仕様変更内容と同様の変更が必要かを確認する。
  2-1. 各箇所について、今回の変更と同様の変更が既に反映されているか／未反映かを個別に判定する。
  2-1-a. 変更前と同じ状態のまま残る同種箇所が、今回変更された箇所と同一の参照元条件（例：参照元の機能有無判定・電源状態・適用条件が一致し、かつ要求廃止でない＝有効）を持つ場合は、反映漏れ（問題あり）とみなす。この場合、変更箇所自身の参照元条件が一見不適切（例：機能有無判定×なのに変更された）であっても、その妥当性は本チェックの範疇外であり、同一条件の未反映箇所を反映漏れとして扱う判断を妨げない。
  2-2. 未反映の箇所がある場合、その箇所に同様の変更が不要である合理的理由（例：当該行の適用条件が成立しない、信号種別/機能区分の違いにより対象外、参照元の該当条件が無効＝要求廃止 等）があるかを確認する。反映要否の判定に参照元条件の確認が必要な場合は参照元を参照し、要求廃止行は無効として扱う。
  2-3. 合理的理由なく未反映の箇所が1つでもあれば「問題あり」、全ての未反映箇所に合理的理由がある（または未反映箇所が無い）場合は「問題なし」と判断する。合理的理由の有無が参照先不在等で確定できない場合は要確認とする。

## `<記載追加の場合>`
変更前に該当記載が存在しない新規追加のため、「変更前の記載」を起点とした抽出は行わず、以下で確認する。
1. 追加された項目（信号名、画面名、要求ID等の識別子）や内容を特定する。
2. 変更後仕様書内(仕様書本体、添付資料を含む)で、追加された項目と同種の既存項目（例：同じ章内の他の信号、同じテーブル内の他の行）が、どの章節・テーブルに記載されているかを網羅的に列挙する（＝セット記載構造の把握）。
3. 既存の同種項目に対し、追加された項目と同様の変更が必要かを判定する。
4. 記載がない箇所がある場合、その箇所への追加が不要である合理的理由（例：当該行の適用条件が成立しない、信号種別/機能区分の違いにより対象外、参照元の該当条件が無効＝要求廃止 等）があるかを確認する。反映要否の判定に参照元条件の確認が必要な場合は参照元を参照し、要求廃止行は無効として扱う。
5. 合理的理由なく未反映の箇所が1つでもあれば「問題あり」、全ての未反映箇所に合理的理由がある（または未反映箇所が無い）場合は「問題なし」と判断する。合理的理由の有無が参照先不在等で確定できない場合は要確認とする。
